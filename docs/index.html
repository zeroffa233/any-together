同步网页资源，不搬运媒体。

AnyTogether 把每个网页里的 资源身份 和 播放器状态 对齐，让大家继续使用自己的原生播放器。媒体留在网页与设备上，网络只传递该同步的状态。

The workflow

先确认“是哪一个资源”，再同步“现在是什么状态”。

同步器不保存 session、revision 或 command。它只理解一个网页如何映射到统一的资源与媒体语义。

01

识别资源身份

从页面 URL 生成可比较的 canonical identity。查询参数、尾部斜杠等不影响同一资源的判断。

02

权威状态排序

Node 伴随进程通过 WebSocket 维护 session、revision 与顺序；它传递播放意图，不传输媒体文件。

03

实际状态回报

页面适配器驱动本地原生播放器，再读取真实结果。漂移、资源不匹配与过渡态会明确反馈。

A small, explicit core

架构只把该负责的事做好。

页面、同步器、权威层各自拥有清晰边界：站点差异留在 adapter，session 一致性留在 authority。

  • 页面层：选择确定的 media target，监听原生事件。
  • 同步器：实现统一 ResourceAdapter 语义，不持有会话状态。
  • 权威层：检查 identity、revision、phase 与实际状态的一致性。
Support, without overclaiming

今天能用什么，和明天想共建什么。

支持范围只反映已经写进实现与测试的能力。网站同步器不是“抓取器”清单，而是一个可审查的社区接口。

Build the next syncer

把站点差异放进同步器，把核心留给所有人。

新同步器只需要实现页面语义；注册表负责 URL 路由与能力声明，核心负责会话一致性。

ResourceAdapter / contractstateless by design
interface ResourceAdapter {
  readonly adapterId: string;
  identifyResource(): ResourceIdentity;
  selectTarget(): void;
  readState(): LocalPlaybackState;
  applyState(target): Promise<AdapterApplyResult>;
  subscribe(listener): () => void;
}

// registration adds adapterId, domain, urlRule,
// create(page) and declared capabilities.

关键：不要在适配器里存 session / revision / command。始终回报页面真实发生了什么。

Roadmap

从可验证的一个站点，走向可维护的同步器社区。

路线图是方向，不是已经交付的能力。每一步都先有明确契约，再有真实页面验证。

Now · baseline

稳住同步核心

把资源 identity、authority 与 adapter 边界做成可测试的基础。

  • Bilibili 视频同步器
  • 动态 resource-bind 与 readiness
  • Node + WebSocket + MV3 扩展路径
Next · verification

把跨站点能力验证清楚

先补真实页面与浏览器生命周期验证，再把已实现的同步器交给更多贡献者使用。

  • YouTube 真实浏览器/跨设备验证
  • 更多页面生命周期验证
  • 贡献新同步器的可重复流程
Later · community

让同步器可共建

形成可审查、可维护、由社区持续验证的站点适配生态。

  • 更多独立贡献者与评审
  • 跨站点的行为测试经验
  • 发布渠道与运营能力待明确

A community-shaped project

每一个网页，都可以拥有自己的同步器。

AnyTogether 的愿景不是把所有媒体搬到一个地方，而是让不同网页在尊重原生播放器的前提下，拥有一套可组合、可验证的同步语言。

START WITH THE CONTRACT 先读 ResourceAdapter 与 SyncerRegistration，再提交真实页面上的行为验证。
